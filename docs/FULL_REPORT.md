# Claude Code 토큰 절약 벤치마크 — 전체 보고서

## 핵심 결과

**코드 작성이 중심인 개발 과제 하나**를 Claude Code에 맡기고 토큰 절약 방법을 비교한
탐색적 실험이다.

- **Headroom `cache`**: 2회 평균 기준 처리 토큰 **36.7% 감소**, API 환산 비용 **26.4% 감소**
- **`be brief`**: 처리 토큰 **17.1% 감소**, 비용 **20.2% 감소**
- **RTK**: 처리 토큰 **30.1% 감소**, 비용 **16.5% 감소**
- **Caveman `full`**: 처리 토큰 **14.7% 증가**, 비용 **3.6% 증가**

Headroom의 비용 절감률은 경계선 수준이었다. 두 실행의 비용 차이가 25.1%나 됐기 때문이다.
반면 매 턴 다시 읽은 컨텍스트는 41.4% 줄었고, Headroom 실행 간 편차도 10.6%로 그리 크지
않았다.

RTK는 cache read 감소분의 85%가 턴 수가 줄어든 데서 나왔다. hook이 실제로 다시 쓴 Bash
command는 7개 중 1개뿐이었다. Caveman은 설명 문장을 줄이기는 했지만, 이 과제에서는 산문이
전체 출력에서 차지하는 몫이 작아 효과가 드러나지 않았다.

품질 점수는 held-out grader로 채점한 실행에서 96~100 사이였다. Headroom 2차 실행은 공개
테스트를 통과했으나 held-out grader로 다시 채점하지는 않았다.

> 여기 적은 비율은 이번 실험에서 관측한 값이다. 일반적인 성능을 보장하는 숫자가 아니다.
> baseline과 Headroom만 각각 2회 반복했고, 나머지 방법은 한 번씩만 관측했다.

## 어떤 조건을 비교했나

수치의 원본은 [`data/published-measurements.csv`](../data/published-measurements.csv)다.
[`GENERATED_RESULTS.md`](GENERATED_RESULTS.md)는 `make report`가 이 CSV에서 만들어 낸다.

| ID | 조건 |
|---|---|
| `BASE-01`, `BASE-02` | 기본 Claude Code |
| `H-ON-01`, `H-ON-02` | 기본 `cache` 모드의 Headroom proxy |
| `C-FULL` | `full` 모드 지시문을 적용한 Caveman plugin |
| `C-BRIEF` | plugin 없이 짧은 간결성 지시문만 추가 |
| `R-ON` | Bash에 걸어 둔 RTK `PreToolUse` hook |

조건이 똑같은 baseline 두 실행은 둘 다 96점을 받았다. 그런데도 턴 수는 37%, 처리 토큰은
22.06%, 비용은 9.78% 벌어졌다. 이 보고서가 단정을 피하는 가장 큰 이유가 이 변동 폭이다.

## 비용은 어떻게 계산했나

비용은 provider가 보고한 **API 환산 추정치**다. 일반 입력, cache 생성, cache 읽기, 출력
비용을 모두 포함한다. Claude Pro 구독료에 추가로 붙는 금액은 아니다.

"처리 토큰"은 이 네 가지 토큰 범주를 합한 값이다. 작업량을 견주기에는 쓸모가 있지만
범주마다 단가가 달라서, 처리 토큰 수가 곧 청구 금액이 되지는 않는다.

## 품질은 어떻게 평가했나

시험 과제는 SQLite 기반 GPU admission service와 다음 산출물을 만들도록 구성했다.

- 애플리케이션과 테스트
- Kubernetes·CI 파일
- 운영 문서

공개 동작 테스트는 볼 수 있게 두었고, 추가 grader 테스트는 실행 중 agent worktree
바깥에 감춰 두었다. 최종 점수는 기능 동작, 필수 파일, 문서, 최종 응답의 근거를 합산했다.

그러므로 이 점수는 이 과제에 맞춰 만든 평가 기준(rubric)이다. 범용 모델 벤치마크 점수로
읽으면 안 된다.

## 각 방법은 실제로 무엇을 줄였나

- **Headroom**: 턴마다 실려 가는 긴 컨텍스트를 줄였다. 요청당 컨텍스트는 확실히 줄었지만
  전체 턴 수가 크게 흔들려 총비용은 상대적으로 불안정했다.
- **`be brief`**: 주로 출력 토큰과 cache 생성 토큰을 줄였다. 가장 단순한 방법이고 plugin도
  필요 없다.
- **RTK**: shell command 출력을 줄이는 도구다. 이번 유효 실행은 짧았던 데다 hook이 실제로
  바꾼 command가 하나뿐이어서, 전체 절감률을 RTK 자체의 근거로 삼기는 어렵다.
- **Caveman `full`**: 설명 문장을 짧게 만들었다. 그러나 코드 작업에서 설명이 차지하는 몫이
  작았고, 늘어난 턴과 컨텍스트가 줄인 만큼을 도로 까먹었다.

## 무효 실행과 총 지출

다섯 번의 시도는 결과에서 뺐다.

1. Headroom prompt가 깨진 실행 1회
2. Headroom·RTK의 `max-turn` 도달 실행 2회
3. RTK의 또 다른 `max-turn` 도달 실행 1회
4. 취소한 baseline 1회

유효 실행 비용은 약 `$11.62`, 모든 시도를 합치면 약 `$18.33`였다. 무효 실행도 실험을
설계하면서 실제로 나간 돈이므로 숨기지 않고 적어 둔다.

## 한계와 재현성

- Headroom은 2회, 나머지 방법은 1회씩만 관측했다. 신뢰구간이나 통계적 유의성을 주장할 수
  없다.
- H-ON-02는 공개 테스트를 통과했지만 held-out grader 품질 점수가 없다.
- prompt를 두 가지 변형으로 썼다. Headroom과 RTK에서는 앞선 실행에서 턴을 낭비하게 만들던
  1,000줄 강제 제한을 뺐으므로, 효과를 온전히 갈라 귀속시킬 수 없다.
- 첫 턴의 cache 상태가 비대칭이었다. 먼저 돌린 세 조건은 cache에서 24,556토큰을 읽었고,
  나중에 다시 돌린 조건은 0토큰을 읽었다. 추정 비용 영향은 실행당 약 $0.0074(0.41%)로,
  측정된 baseline 비용 변동 9.78%보다 작았다.
- **지금 저장소의 harness는 수정된 상태여서, 각 공개 실행 당시와 byte 단위로 같지 않다.**
  공개 실행이 결함을 고쳐 나가는 도중에 이뤄졌기 때문이다. 따라서 지금 트리에서 다시
  돌려도 당시 수치가 그대로 나오지는 않는다. 대신 측정 버그를 고친 벤치마크가 돌아간다.

  고친 내용은 다음과 같다.

  - hidden test는 stdout에서 `"... ok"`를 긁지 않고 JSON result file에서 점수를 읽는다.
  - lock timing 한 번의 운이 점수를 가르지 않도록 5회 실행 후 다수결로 정한다.
  - `max_turns` 도달, 빈 최종 응답, 파일 미변경 실행은 무효로 처리한다.
  - 추적되지 않은 새 파일도 `git add -A -N`으로 stage해 diff와 grader가 볼 수 있게 했다.
  - 겹치던 control 세 가지(`H-OFF`, `C-NON`, `R-OFF`)를 `BASE` 하나로 합쳤다.
  - 변동 폭을 볼 수 있도록 `BASE`와 `H-ON`을 반복했다.
  - prompt의 턴 예산을 실행 설정에서 주입해 `--max-turns`와 어긋나지 않게 했다.
  - hidden CLI test가 prompt에 실제로 적힌 interface를 호출하도록 고쳤다.

  공개 수치를 잰 뒤에도 구조를 손봤다. 결과 해석이 달라지지는 않지만, 다시 돌릴 때
  동작이 달라지는 부분이다.

  - 조건을 Python enum과 분기문에서 `benchmark/config.json` 선언으로 옮겼다. 새 절약법
    추가가 선언 하나로 끝나고, 각 조건이 활성화 슬롯을 하나만 채우므로 "모든 처치는
    baseline에서 한 가지만 다르다"는 설계가 구조로 강제된다.
  - 반복 횟수를 조건 선언의 `repeat`로 옮겼다. 그전에는 순차 runner가 첫 성공에서 다음
    조건으로 넘어가 `BASE`를 1회만 돌렸고, 그러면 실행 간 변동을 잴 수 없었다.
  - 실행 디렉터리를 회차별로 갈랐다. 그전에는 결과 한 벌이 남아 있으면 다음 실험이 "이미
    완료"로 판정돼 아무것도 돌지 않았다.
  - 반복 실행에도 캐시 washout을 적용한다. 그전에는 `repeat`의 2회차가 대기 없이 자기
    1회차 직후에 시작해 그 캐시를 읽었고, 리포트에서는 washout 실패로 찍혔다.
  - transcript를 턴 단위로 갈라 `data/activity-log.csv`에 적는다. 어떤 도구 호출이
    컨텍스트를 얼마나 키웠고 그것이 이후 턴에 몇 번 다시 실렸는지 볼 수 있다. 자세한
    내용은 [활동 단위 토큰 측정](ACTIVITY-LOG.md)에 있다.
  - 실행이 끝나면 `/clear`를 보내던 절차를 없앴다. 판정에 쓰이지 않았고, 없어도
    transcript가 온전하다는 것을 확인했다.

- API를 병렬로 돌리면 service 부하와 rate limit 간섭이 생길 수 있다.
- 이 결과는 여기 쓴 fixture, prompt, model version, effort, tool version에 한정된다.
- 개인정보 보호를 위해 정제한 집계값만 공개하고 raw transcript는 공개하지 않았다. 그래서
  독자가 표를 다시 계산해 볼 수는 있어도, 이 저장소만으로 provider의 모든 event를 독립적으로
  감사할 수는 없다.

## 실용적인 결론

가장 먼저 시도해 볼 만한 것은 단순한 `be brief` 지시문이다. 설치할 것이 없고 필요 없으면
바로 뺄 수 있다.

Headroom은 **턴당 컨텍스트를 거듭 줄이는 효과**를 보였지만 총비용 절감률은 턴 수 변동에
휘둘렸다. RTK와 Caveman은 지금 하려는 작업이 각 도구가 힘을 쓰는 조건에 맞는지 먼저
확인하고 켜는 편이 낫다.

무엇을 실험하든 baseline부터 반복해 보자. 절감 폭이 baseline 변동을 넘지 못하면
"신뢰성 있게 측정되지 않음"이라고 적는 편이 안전하다.
