# Claude Code 토큰 절약 벤치마크 — 전체 보고서

## 핵심 결과

이번 실험은 **코드 작성이 중심인 하나의 개발 과제**를 Claude Code에 맡기고, 토큰 절약 방법을 비교한 탐색적 실험이다.

- **Headroom `cache`**: 2회 평균 기준 처리 토큰 **36.7% 감소**, API 환산 비용 **26.4% 감소**
- **`be brief`**: 처리 토큰 **17.1% 감소**, 비용 **20.2% 감소**
- **RTK**: 처리 토큰 **30.1% 감소**, 비용 **16.5% 감소**
- **Caveman `full`**: 처리 토큰 **14.7% 증가**, 비용 **3.6% 증가**

Headroom의 비용 절감률은 경계선 수준이었다. 두 실행의 비용 차이가 25.1%였기 때문이다. 반면 매 턴 다시 읽은
컨텍스트는 41.4% 줄었고, Headroom 실행 간 편차도 10.6%로 상대적으로 작았다.

RTK는 cache read 감소분의 85%가 더 적은 턴으로 작업이 끝난 결과로 설명됐다. 실제로 hook이 재작성한 Bash command는
7개 중 1개뿐이었다. Caveman은 설명 문장을 줄였지만, 이 과제에서는 산문이 전체 출력에서 차지하는 비중이 작아 효과가
나타나지 않았다.

품질 점수는 held-out grader로 채점된 실행에서 96~100 사이였다. Headroom 2차 실행은 공개 테스트를 통과했지만,
held-out grader로는 다시 채점하지 않았다.

> 여기서 제시한 비율은 이번 실험의 관측값이다. 일반적인 성능을 보장하는 수치가 아니다. Baseline과 Headroom은 각각
> 2회 반복했고, 나머지 방법은 각각 1회만 관측했다.

## 어떤 조건을 비교했나

수치의 기준이 되는 원본은 [`data/published-measurements.csv`](../data/published-measurements.csv)다.
[`GENERATED_RESULTS.md`](GENERATED_RESULTS.md)는 `make report` 명령으로 이 CSV에서 생성된다.

| ID | 조건 |
|---|---|
| `BASE-01`, `BASE-02` | 기본 Claude Code |
| `H-ON-01`, `H-ON-02` | 기본 `cache` 모드의 Headroom 프록시 |
| `C-FULL` | `full` 모드 지시문을 적용한 Caveman plugin |
| `C-BRIEF` | plugin 없이 짧은 간결성 지시문만 추가 |
| `R-ON` | Bash에 적용한 RTK `PreToolUse` hook |

같은 조건의 Baseline 두 실행은 모두 96점을 받았다. 그러나 턴 수는 37%, 처리 토큰은 22.06%, 비용은 9.78% 달랐다.
이 변동 폭이 이 보고서가 단정적인 결론을 피하는 가장 큰 이유다.

## 비용은 어떻게 계산했나

비용은 provider가 보고한 **API 환산 추정치**다. 일반 입력, cache 생성, cache 읽기, 출력 비용을 모두 포함한다.
Claude Pro 구독료에 추가로 청구되는 금액은 아니다.

“처리 토큰”은 이 네 가지 토큰 범주의 합계다. 작업량을 비교할 때는 유용하지만, 범주마다 단가가 다르므로 처리 토큰 수가
그대로 청구 금액이 되는 것은 아니다.

## 품질은 어떻게 평가했나

테스트 과제는 SQLite 기반 GPU admission service와 다음 산출물을 구현하도록 구성했다.

- 애플리케이션과 테스트
- Kubernetes·CI 파일
- 운영 문서

공개 동작 테스트는 확인할 수 있게 두었고, 추가 grader 테스트는 실행 중 에이전트 worktree 바깥에 보관했다. 최종 점수는
기능 동작, 필수 파일, 문서, 최종 응답의 근거를 합산했다.

따라서 이 점수는 해당 프로젝트에 맞춘 평가 기준(rubric)이다. 범용 모델 벤치마크 점수로 보면 안 된다.

## 각 방법은 실제로 무엇을 줄였나

- **Headroom**: 턴마다 전달되는 긴 컨텍스트를 줄였다. 요청당 컨텍스트는 확실히 감소했지만, 전체 턴 수는 크게 달라져
  총비용은 상대적으로 불안정했다.
- **`be brief`**: 주로 출력 토큰과 cache 생성 토큰을 줄였다. 가장 단순한 방법이고 plugin도 필요 없다.
- **RTK**: shell command 출력을 줄이는 도구다. 이번 유효 실행은 짧았지만 hook이 실제로 바꾼 command가 하나뿐이어서,
  전체 절감률을 RTK 자체의 강한 근거로 보기는 어렵다.
- **Caveman `full`**: 설명 문장을 짧게 만들었다. 그러나 코드 작업에서 설명이 차지하는 비중이 작았고, 더 많은 턴과
  컨텍스트가 절감분을 상쇄했다.

## Headroom 재실행 결과

### 실행별 수치

| 실행 | 비용 | 턴 수 | 턴당 비용 | 턴당 컨텍스트 | 출력 토큰 |
|---|---:|---:|---:|---:|---:|
| H-ON-01 | $1.218 | 28 | $0.0435 | 46,131 | 35,311 |
| H-ON-02 | $1.567 | 48 | $0.0327 | 41,479 | 44,596 |
| BASE-01 | $1.799 | 30 | $0.0600 | 77,901 | 51,826 |
| BASE-02 | $1.984 | 41 | $0.0484 | 71,634 | 47,645 |

### 두 조건을 비교하면

| 지표 | H-ON 대 BASE | H-ON 편차 | BASE 편차 | 범위 겹침 | 평가 |
|---|---:|---:|---:|---|---|
| 총비용 | -26.4% | 25.1% | 9.8% | 없음 | 경계선 |
| 턴당 비용 | -29.7% | 28.5% | 21.4% | 없음 | 경계선 |
| 턴당 컨텍스트 | -41.4% | 10.6% | 8.4% | 없음 | 견고 |
| 출력 토큰 | -19.7% | 23.2% | 8.4% | 없음 | 변동 범위 내 |

처음에는 Headroom 단일 실행만 보고 비용이 35.6% 줄었다고 계산했다. 하지만 재실행을 포함하면 평균 절감률은
26.4%로 낮아졌다.

그렇다고 효과가 사라진 것은 아니다. Headroom의 두 비용 `$1.218`, `$1.567`은 Baseline의 `$1.799`, `$1.984`보다
모두 낮았다. 네 번의 관측에서 두 조건의 비용 범위도 겹치지 않았다.

가장 안정적인 결과는 **턴당 컨텍스트 41.4% 감소**였다.

- Headroom: 41,479~46,131토큰
- Baseline: 71,634~77,901토큰
- Headroom 내부 편차: 10.6%

즉 Headroom이 일관되게 줄인 것은 작업을 끝내는 데 필요한 턴 수가 아니라, 매 요청에 다시 전달되는 컨텍스트 크기였다.
총비용은 턴 수가 28~48회로 달라지면서 함께 흔들렸다.

H-ON-02의 optimizer log도 H-ON-01과 같은 패턴을 보였다. 35개 요청에서 요청당 9,848토큰을 제거했고, 첫 실행에서는
요청당 8,934토큰을 제거했다. 사용한 변환도 동일하게 `tool_schema_compaction`과 `tool_search_deferral`이었다.

## 무효 실행과 총 지출

다섯 번의 시도는 결과에서 제외했다.

1. Headroom prompt가 손상된 실행 1회
2. Headroom·RTK의 `max-turn` 도달 실행 2회
3. RTK의 또 다른 `max-turn` 도달 실행 1회
4. 취소한 Baseline 1회

유효 실행 비용은 약 `$11.62`, 모든 시도를 합친 비용은 약 `$18.33`였다. 무효 실행도 실험을 설계하는 과정에서 실제로
발생한 운영 비용이므로 숨기지 않고 기록했다.

## 한계와 재현성

- Headroom은 2회, 나머지 방법은 각각 1회만 관측했다. 따라서 신뢰구간이나 통계적 유의성을 주장할 수 없다.
- H-ON-02는 공개 테스트를 통과했지만 held-out grader 품질 점수가 없다.
- 프롬프트 변형을 2개 사용했다. Headroom과 RTK는 이전 실행에서 턴을 낭비하게 만든 강제 1,000줄 제한을 제거했으므로,
  효과를 완전히 분리해 귀속할 수 없다.
- 첫 턴의 cache 상태가 비대칭이었다. 먼저 실행한 세 조건은 cache에서 24,556토큰을 읽었고, 나중에 재실행한 조건은
  0토큰을 읽었다. 추정 비용 영향은 실행당 약 $0.0074(0.41%)로, 측정된 Baseline 비용 변동 9.78%보다 작았다.
- **현재 저장소의 harness는 수정된 상태이며, 각 공개 실행 당시의 상태와 byte 단위로 동일하지 않다.** 공개 실행은 결함을
  수정하는 과정에서 수행됐기 때문이다. 따라서 현재 tree에서 다시 실행해도 당시 수치를 정확히 재현하지는 못한다. 대신
  측정 버그를 수정한 벤치마크를 실행한다.

  수정한 내용은 다음과 같다.

  - hidden test는 stdout에서 `"... ok"`를 파싱하지 않고 JSON result file에서 점수를 읽는다.
  - lock timing 변동 하나가 점수를 결정하지 않도록 5회 실행 후 다수결을 사용한다.
  - `max_turns` 도달, 빈 최종 응답, 파일 미변경 실행은 무효 처리한다.
  - 추적되지 않은 새 파일도 `git add -A -N`으로 stage해 diff와 grader가 확인할 수 있게 한다.
  - 중복 control 세 가지(`H-OFF`, `C-NON`, `R-OFF`)를 하나의 `BASE`로 합쳤다.
  - 변동 폭을 확인할 수 있도록 `BASE`와 `H-ON`을 반복했다.
  - 프롬프트의 턴 예산을 실행 설정에서 주입해 `--max-turns`와 불일치하지 않게 했다.
  - hidden CLI test가 프롬프트에 실제로 명시된 interface를 호출하도록 수정했다.

- API를 병렬 실행하면 service 부하와 rate limit 간섭이 생길 수 있다.
- 이 결과는 해당 fixture, prompt, model version, effort, tool version에만 적용된다.
- 개인정보 보호를 위해 정제한 집계값만 공개하고 raw transcript는 공개하지 않았다. 따라서 독자는 표를 다시 계산할 수는 있지만,
  이 저장소만으로 provider의 모든 event를 독립적으로 감사할 수는 없다.

## 실용적인 결론

가장 먼저 시도할 방법은 단순한 `be brief` 지시문이다. 설치할 것이 없고, 필요하면 바로 제거할 수 있다.

Headroom은 **턴당 컨텍스트를 반복해서 줄이는 효과**를 보였지만, 총비용 절감률은 턴 수 변동에 민감했다. RTK와 Caveman은
작업이 실제로 각 도구의 작동 조건을 만족하는지 확인한 뒤에 켜는 편이 좋다.

실험할 때는 먼저 Baseline을 반복 실행하자. 절감 폭이 Baseline 변동을 넘지 못하면 “신뢰성 있게 측정되지 않음”이라고
보고하는 것이 안전하다.
